1. System context and design principles

Home Lab Hub is a self-hosted application platform: a three-node Kubernetes cluster on commodity mini PCs that runs a family business's line-of-business apps, home automation and video surveillance, behind a single portal (hub.energiapower.llc) with centralized identity. The "hub" is both the portal application (Next.js) and, by extension, the platform it fronts.

Design principles (and the decisions they drove)

PrincipleConcrete decision
Zero inbound exposureCloudflare Tunnel (outbound-only) instead of port forwarding. UPnP removed from the router. Admin-only tools without a public route (Argo CD) are LAN-only.
Git is the source of truthEvery workload is an Argo CD Application with selfHeal: true. Secrets are committed as SealedSecrets. Image versions are pinned in git (with one exception, §7).
Centralized identity, minimal double loginAuthentik is the IdP. Apps with mature auth keep their own login (no ForwardAuth layered on top), while tools without auth (Prometheus, Alertmanager, Frigate, Longhorn) sit behind Authentik ForwardAuth.
Least privilege for the internet-facing portalThe hub can read backup state and create snapshots and backups, but cannot delete or restore. Destructive storage operations stay in Longhorn behind a step-up 2FA flow.
Recoverability is tested, not assumedNightly Longhorn backups to separate hardware, plus scripted restore tests that compare restored data against live data.
Supply-chain hygieneActions pinned by commit SHA; images pinned by tag or digest; third-party HA integrations installed by pinned version and SHA-256; Trivy, Gitleaks and Semgrep in CI.
Commodity hardware, graceful degradationThree nodes with Longhorn 3-replica volumes for important data; cheaper single-replica class (longhorn-single) for bulk, re-creatable data such as camera media.

2. Physical and network topology

Notes engineers must know

  • Router isolation, not firewall rules. On SRM 1.3, firewall rules don't filter traffic between local networks; the per-network isolation checkbox does. The six firewall rules created during setup are inert. Isolation is on for all three networks.
  • Calico address autodetection is pinned (cidrs: 192.168.1.0/24). Without this, Calico could pick worker-02's IOT Wi-Fi address as the node IP and break pod networking. This setting lives in the cluster only (documented in the README); see §14.
  • worker-02 nftables guard (/etc/iot-wifi-guard.nft, systemd iot-wifi-guard): drops new inbound connections from the IOT VLAN except UDP from the two Wyze cameras, and blocks the camera-bridge ports on eno1 (TCP 1935, 1984, 5000, 5080, 8554, 8888, 8889, 9997; UDP 8000, 8001, 8189). Changes are validated with nft -c against a temporary file before install (scripts/worker-02-firewall.sh).
  • Node pinning. Home Assistant (hostNetwork, needs LAN discovery and a stable address) and Frigate (needs the iGPU and is in the camera firewall allow-list) are pinned to worker-02. Authentik has node affinity that keeps it off the memory-constrained control plane.

Resource posture

The workers have headroom (about 46–57% memory used). openclaw is the constraint: 8 GB, typically 66–79% used, of which roughly 1.8 GB is the k3s server process and about 3.5 GB sits outside pods. Treat new DaemonSets and any workload without node affinity as a risk to the control plane. Most workloads run a single replica without PodDisruptionBudgets, so a node drain causes short outages (acceptable for a home lab, and noted in §14).

4. Edge, ingress and request routing

All public hostnames are under energiapower.llc, proxied by Cloudflare. cloudflared (2026.10.3, token-managed, namespace default) holds an outbound tunnel; the hostname → origin routes are configured in the Cloudflare dashboard, not in git (§14). There are two routing patterns:

PatternTunnel originUsed by
A. Direct to Servicehttp://<svc>.<ns>.svc.cluster.localApps with their own login: hub, CRM, Investco, Petros (ai.), PDF Edit, Godseye, website, Grafana, Authentik, Home Assistant.
B. Through Traefik + ForwardAuthhttps://traefik.traefik.svc.cluster.local:443, "No TLS Verify", Host header preservedApps with no login of their own: Prometheus, Alertmanager, Frigate, Longhorn.
Rule: never point a pattern-B hostname straight at its Service.Doing so skips the ForwardAuth middleware and publishes an unauthenticated admin tool to the internet. This applies especially to Longhorn, which can delete backups.

Operational gotchas

  • Renaming a tunnel route can leave its DNS record missing. Check authoritative DNS, and find the active hostnames in cloudflared's "Updated to new configuration" log line.
  • Home Assistant sees traffic from pod and node addresses: trusted_proxies (10.42.0.0/16 plus the three node IPs) is set in the HA UI, because HA 2026.10 ignores the YAML http: block after a one-time import.
  • LAN-only access to the hub (hub.192.168.1.243.nip.io) goes through a Traefik Ingress. Public access goes through the tunnel (pattern A).

Hub authentication

The hub is an OIDC relying party using next-auth 4 (stable line). src/proxy.ts (the Next.js 16 replacement for middleware.ts) requires a session token on every route except /api/auth, /api/health, /sign-in and static assets. Authorization (src/lib/access.ts) maps the groups claim to tile audiences server-side: hidden tiles are never sent to the browser. Sign-out is hub-only by design; the Authentik session lasts until the browser closes.

Why not ForwardAuth for everything?Apps with their own auth (CRM, Investco, Petros…) would force a double login, and Home Assistant's companion app can't complete a browser-based ForwardAuth flow. The rule is: ForwardAuth only for software that has no authentication of its own.

6. The hub application

  • Next.js 16.4.5, React 19.3, TypeScript 5, App Router. Read node_modules/next/dist/docs before coding: this major version has breaking changes (see AGENTS.md).
  • PostgreSQL 17.11 StatefulSet in hub, accessed with the postgres (porsager) client.

Data model and migrations

Migrations are an ordered array of SQL strings in src/lib/migrate.ts, applied once each at startup inside a transaction guarded by pg_advisory_xact_lock (safe with concurrent pods) and recorded in schema_migrations. Never edit an existing migration; append a new one. Tables: apps (name, description, url, status_url, category, audience, hidden, sort_order) and audit_log (actor, action, target, detail jsonb). Every change made through Manage writes an audit row.

Status, health and backups

  • Tile status lights probe each app's status_url from inside the cluster (Service DNS), not its public URL, so a Cloudflare problem doesn't show as an app outage. The page refreshes every 30 seconds.
  • Health page reads node and pod metrics through the Kubernetes API using the pod's ServiceAccount token (lib/kube.ts), with per-node pod usage (buildWorkloads).
  • Backups page reads Longhorn volumes, backups, backuptargets and snapshots, and can create snapshots and backups. The RBAC is a namespaced Role in longhorn-system (platform/longhorn-backup/manifests/hub-backup-access.yaml) with verbs get, list and create only: no delete, no restore.

Router files, Trash, recycle bins and the media backup (Phases 6–7)

The hub pod has a second container, files (rclone 1.69.1), that logs in to the router's SMB server (SMB 2.0.2, 192.168.1.1) as the hub's own SRM account. It serves every share that account can open as one WebDAV tree on 127.0.0.1:8091 (downloads, uploads, renames via MOVE) plus rclone's remote-control API on 127.0.0.1:5572 (listings, sizes, deletes, background jobs). Nothing outside the pod can reach either port. Shares in FILES_HIDDEN (k8s-storage-folder, camera-clips, media-backup) never appear in the UI.

Extending the hub: checklist

  1. Pure logic goes in src/lib/*.ts with a matching *.test.ts. UI in src/app. Server components by default.
  2. Schema change: append to migrations. Data change: through Manage (audited), not SQL.
  3. Needs a new Kubernetes permission: add a narrowly scoped Role in the namespace that owns the resource, never a ClusterRole with wildcards.
  4. Run locally: npm run lint && npm run typecheck && npm test && npm run build. CI runs the same steps plus npm audit, Gitleaks and Semgrep.

Release engineering conventions

  • Third-party Actions are pinned by commit SHA, with the version in a comment. Renovate (hub repo only) proposes bumps. The protect-main ruleset blocks deletion and force-push; PR and status-check rules are deliberately off so the bot's pin commit isn't blocked.
  • Bot commits must not trigger a release loop: commits made with GITHUB_TOKEN don't start workflows, and [skip ci] covers it anyway. Before committing locally, pull first.
  • Rollback = revert the bot's pin commit (or set the previous tag) and let Argo CD sync. Never kubectl set image: selfHeal reverts it.
  • Petros CI uses the production database (DATABASE_URL secret) for the login test. Test isolation is a roadmap item.

Off-site copy (Cloudflare R2)

CronJob longhorn-system/offsite-backup runs at 05:30 New York, after the 03:30 backups (platform/longhorn-backup/manifests/offsite-backup.yaml; rclone 1.69.1 on openclaw, as root only to read the 0600 etcd snapshot files through a read-only hostPath). Credentials and the encryption password and salt are in the SealedSecret offsite-backup (scripts/seal-offsite-backup.ps1). The password and salt are also in the owner's password manager, because after a total loss the cluster holding the sealed copy is gone too.

  • What: the router's k8s-storage-folder (the Longhorn backup store, all volumes) and the k3s etcd snapshots (every object and Secret, including the Sealed Secrets key).
  • Encryption: rclone crypt (file contents and names) before upload, to r2:home-lab-backups/home-lab. The R2 token is limited to that one bucket, Object Read & Write.
  • Retention: files that change or disappear on the router go to longhorn-replaced/<date>/ for 14 days (the ransomware and accidental-delete window); etcd snapshots are kept 30 days. --fast-list keeps Class A operations low.
  • Size and cost: ~1.4 GB at first, projected 2.5–4 GB at steady state, inside R2's free 10 GB (then $0.015/GB-month, no egress fees).
  • Checks: step 4 of every run compares every router file with the off-site copy by size. Alerts fire if the job fails or is overdue, only while the CronJob isn't suspended.
  • etcd snapshots are compressed by k3s since Nov 12 (etcd-snapshot-compress: true in /etc/rancher/k3s/config.yaml on openclaw, not in git): 44.5 MB → ~7.4 MB each. k3s server --cluster-reset --cluster-reset-restore-path=<file>.zip reads them directly.
  • Turning it off: set suspend: true, empty the bucket (lifecycle rule or rclone purge), delete the bucket and token, and optionally cancel the R2 subscription.

Grafana left the nightly backup on Nov 12. All 25 dashboards and the Prometheus and Alertmanager data sources come from the Helm chart, the Loki data source is provisioned from platform/monitoring-access/manifests/grafana-loki-datasource.yaml (same uid), and the rest of the volume is plugins Grafana downloads again. Note that Longhorn's dataStored figures are uncompressed: measure the backup store itself for real sizes.

Restore procedure (reference)

1. Longhorn UI (step-up 2FA) or kubectl: find the backup URL for the volume (backups.longhorn.io, label backup-volume=<pv>).
2. Create a StorageClass with parameters.fromBackup=<url> (see restore-test scripts), then a PVC from it.
3. Scale the app's StatefulSet to 0, swap the claim (or copy data), scale back to 1.
4. Verify with the matching restore-test fingerprint, then remove the temporary StorageClass.

After a total loss (from the off-site copy), on any machine with rclone:
1. Remotes: r2 = S3, provider Cloudflare, endpoint https://<account-id>.r2.cloudflarestorage.com, with a
   new R2 token for the bucket; offsite = crypt over r2:home-lab-backups/home-lab with the saved password
   and salt (rclone obscure both), standard filename encryption, directory names encrypted.
2. rclone copy offsite:etcd <dir>, then on a fresh k3s server:
   k3s server --cluster-reset --cluster-reset-restore-path=<dir>/<newest>.zip
   (brings back every object, every Secret and the Sealed Secrets key).
3. rclone copy offsite:longhorn <share>, point a Longhorn backup target at that share and restore
   the volumes as above.

11. Camera and IoT subsystem

NetworkPolicies: Frigate UI 8971 from traefik and hub only; Frigate API 5000 and RTSP 8554 from Home Assistant's node address (192.168.1.102) only; blink-bridge 8554 from the cameras namespace and Home Assistant; Mosquitto from the camera namespace and Home Assistant.

The Blink bridge (custom component)

Blink has no local streaming. platform/cameras/manifests/blink-bridge/bridge.py holds a single Blink session token (password never stored) and serves each camera as MPEG-TS on a localhost TCP port (18001–18003). The go2rtc sidecar turns that into RTSP using ffmpeg:tcp://127.0.0.1:1800x#video=copy#audio=aac; the audio is re-encoded because Blink's AAC arrives with a 0/0 sample rate. Dependencies are installed with pip --require-hashes, and the code ships as a kustomize configMapGenerator, so a code change rolls the pod.

  • Battery protection: a battery camera's port refuses players unless a session is running, so Frigate's reconnect attempts can never wake a camera. Sessions start only from the MQTT Start button or a Blink motion event.
  • Sync Module arbitration: Blink allows one live view per Sync Module. A wired camera steps aside while a battery camera on the same network_id is in session, and resumes about 2 seconds after it ends.
  • Reconnect tolerance: a 20-second player grace period, a prewarm buffer for players that connect late, Frigate stream #timeout=30 and ffmpeg -timeout 30000000. The bridge sets go2rtc preloads through the local API (wired cameras always; battery cameras while live), so go2rtc's fixed 5-second DESCRIBE deadline is always met.
  • Upstream patch: blinkpy 0.25.9's recv uses read(n) and treats split TCP segments as end-of-stream. The bridge replaces it with a readexactly loop. Re-check this when upgrading blinkpy.

Known gotchas

  • Git Bash on Windows rewrites absolute paths in kubectl exec arguments: set MSYS_NO_PATHCONV=1. PowerShell 5.1 drops double quotes from native arguments: pipe SQL through stdin.
  • kustomize paths must be Windows-style when running locally. Argo CD prunes generated ConfigMaps only on apps with prune: true.
  • The Wyze bridge log contains auth material: always filter [AUTH] and "Auth [" lines when reading it.

16. Platform evolution beyond the phases

16.1 Everything in git

  • App-of-apps / ApplicationSet: a root Application in this repo generates every app's Application (git generator over a list of repos), removing the hand-applied argocd-application.yaml step.
  • Helm releases under Argo: kube-prometheus-stack, Loki, Promtail, Longhorn and Traefik as Argo Helm sources with values files in platform/.
  • Cloudflare as code: Terraform (or the cloudflared config-file mode) for tunnel ingress rules and DNS, reviewed in pull requests, so pattern-B routing can be checked automatically.

16.2 One release workflow for every app

Converge on the Petros model as a reusable workflow in a shared .github repository: SemVer from VERSION plus tags, build once, test inside the image, Trivy gate, push an immutable tag, bot commit the pin plus a git tag, Argo sync. Then retire Image Updater (or switch it to write-back git). Add post-deploy smoke checks (Argo PostSync hook jobs that hit /health and assert the version) and automatic rollback on failure.

16.3 Environments and test data

  • Ephemeral CI databases (service containers) for Petros and others; seed scripts instead of production data.
  • A staging namespace per app (<app>-staging) deployed from a staging branch, reachable only on the LAN or through Authentik. Promotion = merge to main.
  • QA Lab pattern (registry + background runner + live progress) generalized as a shared test-harness service for the business apps.

16.4 Observability maturity

  • App metrics (OpenTelemetry SDK → Prometheus) for request rate, errors and latency; SLOs for the hub and CRM with burn-rate alerts.
  • Distributed tracing (Tempo) once there are service-to-service calls (the broker agent, MLflow).
  • A hub "Platform status" page backed by Prometheus queries instead of ad-hoc probes.

16.5 AI and ML workloads

  • MLflow for Petros: tracking server (Postgres backend, artifacts on GCS or the Phase 6 share), Authentik-protected UI, Petros training runs logging parameters, metrics and model artifacts; the model registry replaces ad-hoc agent_models versioning.
  • Energy-broker agent (RFP → contract): a new app on the standard template, using the CRM's data through an API (not shared database access), human-in-the-loop approval, and audit logging consistent with the hub.
  • GPU capacity is limited to the Intel iGPUs (used by Frigate). Training-heavy work should stay on cloud GPUs, with only inference and tracking running here.

16.6 Hub product features

  • Ingress / Service auto-discovery (proposed tiles from LoadBalancer Services and tunnel routes), drag-and-drop ordering, per-user favourites.
  • Family self-service: invite flow from the hub through the Authentik API (admins only), a device and camera summary widget, a Phase 6 drives widget.
